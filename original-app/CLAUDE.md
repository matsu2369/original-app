# CLAUDE.md — 財務資料統一フォーマット変換アプリ

このファイルは、Claude Code がこのリポジトリで開発作業を行う際の参照ドキュメントです。
要件変更・機能追加のたびに、該当セクションを更新してください。

---

## 1. プロジェクト概要

取引先から様々な形式(PDF/Excel/CSV)で届く財務資料(有価証券報告書、決算書、興信所調査書など)を、
自動読み取り(OCR/パース)によって社内共通の統一フォーマットに変換し、
社内データベース登録用のExcelファイルを出力するWebアプリケーション。

- **リポジトリ構成**: Next.js (App Router) + Supabase の構成で開発する
- **要件定義書**: 本ファイルの元になった要件定義書は `docs/requirements.md` 等に保管想定(未配置の場合は本セクションが正)
- **開発フェーズ**: MVP開発中(セクション7参照)

---

## 2. アプリのゴール(WHO / WHAT / HOW)

| 観点 | 内容 |
|------|------|
| **WHO(誰のため)** | 取引先の与信・格付け業務を担当する社内担当者(現在は利用者本人1名、将来は全社員) |
| **WHAT(何を解決するか)** | バラバラな書式の財務資料を手作業で統一フォーマットに転記する手間・ミスをなくす |
| **HOW(どう実現するか)** | 資料をアップロード → 自動読み取り・自動変換 → 画面上で確認・修正 → 社内Excelテンプレート形式で出力、という一連のフローをアプリ内で完結させる |

**成功の定義**: 資料が届いてから統一フォーマットのExcelが出力されるまでの一連の作業が、
アプリなしの手作業と比べて大幅に短時間・低ミス率で完了できること。

## 3. ターゲットユーザー詳細

### 現在(フェーズ1)
- 利用者は本人1名のみ
- アカウント管理・権限管理は不要(単一ユーザー利用を前提にシンプルに作る)

### 将来(フェーズ2以降)
- 全社展開し、複数人が同時に利用
- 複数アカウント管理・利用者管理機能が必要になる(セクション7「将来機能」参照)
- 利用者像: 経理・与信管理・審査部門など、取引先の財務資料を日常的に扱う社内担当者
- ITリテラシー: 業務システムやExcelには慣れているが、専門的なITスキルは前提としない

### データ閲覧権限
- 現在・将来ともに**閲覧制限は設けない**方針(全ユーザーが全データを閲覧可能)
- ただし将来的に閲覧制限が必要になった場合に備えた設計(セクション7 Phase2 No.7)は考慮しておく

## 4. 主要機能

### 4.1 MVP(最初に絶対必要な機能)

| # | 機能 | 概要 |
|---|------|------|
| 1 | 資料アップロード機能 | 有価証券報告書(PDF/Excel/CSV)を単数・複数まとめてアップロード可能 |
| 2 | 自動読み取り・変換機能 | アップロードされた資料の内容を自動読み取りし、統一フォーマットへ変換 |
| 3 | 処理済み資料の一覧表示 | 変換済み資料をリスト表示(1資料=1レコード。複数資料を1件に統合しない) |
| 4 | 一覧への項目入力機能 | 一覧の各行で「依頼部署」「取引先コード」「現格付」「備考」を入力・編集可能 |
| 5 | プレビュー機能 | 一覧の行をクリックすると全画面プレビューで内容を確認できる |
| 6 | 読み取り結果の修正機能 | 自動読み取り結果に誤りがあれば画面上で修正可能 |
| 7 | 統一フォーマット出力機能 | 既存の社内Excelテンプレートに沿った形式でファイルを出力 |

### 4.2 対象資料の詳細(MVPスコープ)

- **資料種類**: 有価証券報告書(Phase 2で決算書・興信所調査書に対応拡大)
- **ファイル形式**: PDF / Excel / CSV
- **資料の性質**: 大半はPC作成のクリーンなテキスト。一部、紙スキャンの読み取りづらい資料も含む
  → MVPではクリーンな資料の読み取り精度を優先し、スキャン資料の精度向上はPhase 2以降で対応
- **勘定科目**: 資料ごとに書式がバラバラ → 統一フォーマットへのマッピング処理が必須要件
- **データ単位**: 資料1件につき1レコード(複数資料の統合は行わない)

### 4.3 将来機能(Phase 2以降・優先度目安順)

| # | 機能 | 備考 |
|---|------|------|
| 1 | 決算書への対応 | 対象資料種類の拡大 |
| 2 | 興信所調査書への対応 | 対象資料種類の拡大 |
| 3 | スキャン画像資料の読み取り精度向上 | OCR精度改善 |
| 4 | 社内Webシステムへの自動アップロード連携 | 出力後の後続フローの自動化 |
| 5 | アプリ内データ蓄積・検索機能 | 社内DB的な使い方への発展 |
| 6 | 複数アカウント・利用者管理機能 | 全社展開に向けた対応 |
| 7 | 閲覧制限・アクセス権限管理 | 必要になった場合のみ対応(現時点では不要) |

> **実装時の注意**: MVPの設計時点から、将来のPhase 2機能(特に資料種類の拡大・複数ユーザー化)を
> 阻害しないデータモデル・アーキテクチャにしておくこと。ただし、Phase 2機能自体をMVPで先取り実装しない。

## 5. 主な処理フロー(MVP)

```
1. ユーザーが有価証券報告書(PDF/Excel/CSV)をアップロード(1件 or 複数件)
        ↓
2. アプリが内容を自動読み取りし、統一フォーマットへ変換
        ↓
3. 処理済み資料が一覧表示される(1資料=1行)
        ↓
4. 各行に「依頼部署」「取引先コード」「現格付」「備考」を入力
        ↓
5. 行をクリック → プレビュー画面で全画面確認
        ↓
6. 読み取り誤りがあれば画面上で修正
        ↓
7. 既存の社内Excelテンプレート形式でファイル出力
```

- この一連のフローが**1件のみの処理**でも**複数件まとめての処理**でも成立することが必須要件
- 利用シーンは「新しい取引先の資料が届いたタイミングでの都度処理」

## 6. UI/UX方針

- **シンプルさ優先**: 現在の利用者は1名で、専門知識前提のUIでよいが、将来の全社展開を見据え直感的な操作性を保つ
- **一覧 → プレビュー → 修正 → 出力** の一方向フローをUI上でも明確に表現する
- 一覧画面は資料ごとに1行、行内で主要項目(依頼部署/取引先コード/現格付/備考)をインライン編集可能にする
- プレビューは全画面表示とし、元資料と読み取り結果を対比しながら確認・修正できることが望ましい
- 複数件アップロード時の進捗(読み取り中/完了/エラー)が一覧上で判別できるようにする
- 権限・ログイン画面は将来の複数ユーザー化を見据えて既存のSupabase Auth機能を活かすが、
  MVPでは閲覧制限のUIは作らない(全データ閲覧可能が前提)

## 7. 技術仕様

### 7.1 スタック(現行リポジトリ構成)

- **フレームワーク**: Next.js (App Router) + TypeScript
- **UI**: Tailwind CSS + shadcn/ui (Radix UIベース, `components.json` 設定済み)
- **バックエンド/DB/認証**: Supabase (`@supabase/ssr`, `@supabase/supabase-js`)
- **スタイル**: `class-variance-authority`, `clsx`, `tailwind-merge`
- **アイコン**: `lucide-react`
- **テーマ**: `next-themes`(ダーク/ライト切替対応)

### 7.2 開発コマンド

```bash
npm run dev     # 開発サーバー起動
npm run build   # 本番ビルド
npm run start   # 本番サーバー起動
npm run lint    # ESLint実行
```

### 7.3 MVP実装で必要になる主な技術要素

- **ファイルアップロード**: PDF/Excel/CSVの複数ファイルアップロード(Supabase Storage等の利用を検討)
- **資料解析**:
  - PDF/Excelのテキスト・表構造抽出
  - スキャンPDFなど画像ベース資料へのOCR(MVPでは簡易対応、精度向上はPhase 2)
  - 資料ごとに異なる勘定科目表記 → 統一フォーマットへのマッピングロジック
- **データモデル**: 資料1件 = 1レコード。将来の資料種類拡張(決算書/興信所調査書)・複数ユーザー化を
  見据えたスキーマ設計(例: 資料種別カラム、アップロードユーザーカラムを最初から持たせておく等)
- **Excel出力**: 既存の社内Excelテンプレートに沿ったファイル生成(テンプレートファイルの取り扱いに注意)
- **認証**: Supabase Authをそのまま活用(MVPでは単一ユーザー運用、将来の複数アカウント対応の土台とする)

### 7.4 データ・権限方針

- 閲覧制限なし(全ユーザーが全データを閲覧可能) — 現在・将来共通の方針
- ただし、将来的にアクセス権限管理が必要になった場合に対応できるよう、
  データ所有者・作成者などのメタ情報はレコードに保持しておくことが望ましい

## 9. 成功基準

### MVPの成功基準
- 有価証券報告書(PDF/Excel/CSV)を1件でも複数件でもアップロードでき、エラーなく処理が完了する
- 自動読み取りにより、主要な財務項目(勘定科目・金額等)が統一フォーマットへ変換される
- 一覧画面で処理済み資料を確認でき、「依頼部署」「取引先コード」「現格付」「備考」を入力できる
- 一覧から任意の資料をクリックし、全画面プレビューで内容を確認できる
- 自動読み取りの誤りを画面上で修正でき、修正内容が出力ファイルに反映される
- 既存の社内Excelテンプレートに沿った形式でファイルが出力され、社内データベース登録にそのまま使える品質である

### 中長期の成功基準
- Phase 2対応後、決算書・興信所調査書についてもMVPと同等の精度・使い勝手で処理できる
- スキャン資料の読み取り精度が実用レベルまで向上する
- 全社展開後も複数ユーザーが問題なく同時利用でき、必要に応じて閲覧制限を追加できる拡張性を維持している
